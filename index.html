Ingeniería asistida por IA

La IA es un colaborador dentro de un proceso de ingeniería, no un reemplazo del proceso.

Especificar→Dar contexto→Planear→Ejecutar→Verificar→Revisar

El ingeniero diseña el sistema alrededor del modelo.

Hacer ingeniería con IA = gestionar qué entra a la RAM.

Memoria de corto plazo

Es la ventana de contexto de la sesión actual.

  • Historial de la conversación
  • Archivos leídos, salidas de comandos
  • Tiene un límite (p. ej. 200K – 1M tokens)
  • Se degrada: entre más ruido, peor atención (context rot)

Técnicas

  • Compactar / resumir la conversación
  • Sesiones cortas y enfocadas
  • Limpiar el contexto entre tareas
  • Listas de tareas (TODO) dentro de la sesión

Memoria de largo plazo

Lo que sobrevive entre sesiones y entre personas del equipo.

Todo lo que rodea al modelo y lo convierte en un agente útil.

Herramientas Permisos Hooks Sandbox Skills Loop agente

El mismo modelo rinde muy distinto según el harness.

El Agent SDK no es un harness para abrir y programar: es la librería para construir uno. Los que la gente abre todos los días están en la diapositiva siguiente.

Harness que usa la gente

HarnessQué aportaHerramienta
Claude Code El de Anthropic. Skills, hooks, permisos y subagentes, en la terminal y en el editor. code.claude.com
Codex El de OpenAI. CLI abierta, con sandbox y aprobación por acción. openai/codex
OpenCode Abierto y sin modelo fijo. El que se recomienda para no quedar atado a un proveedor. opencode

Gentle Shell El de Gentleman, sobre Pi. Memoria, ODD y varios agentes en la misma terminal. gentle-shell

gentle-ai no es un harness. Configura los que ya tenés: Claude Code, Cursor, OpenCode, Codex, Pi y otros. Gentle Shell sí es el harness propio de Gentleman, construido sobre Pi, y el instalador le adjunta Engram y gentle-ai. Pi, de Mario Zechner y ahora Earendil, es el harness mínimo que la comunidad usa de base. Gentle Shell es un ejemplo de "hacerlo tuyo". En los rankings de 2026 el primer grupo es Claude Code y Codex. OpenCode es el abierto que más se recomienda para cambiar de modelo. Cursor y Copilot siguen siendo los del editor. Cline es la alternativa abierta dentro del IDE. Devin, Goose y Hermes también circulan. Quedaron afuera para no mezclar agentes de propósito general con los de programar.

Human-in-the-loop

La IA acelera; el humano decide y es responsable.

1Aprobar el plan
2Autorizar acciones riesgosas
3Revisar el diff
4Validar en CI / staging
5Merge y deploy

Más autonomía donde el riesgo es bajo, más control donde es alto.

Todo junto: un flujo real

  1. Memoria El agente carga CLAUDE.md con las reglas del repo
  2. Contexto Recibe un ticket claro + archivos relevantes
  3. Orquestación Un subagente explora, otro propone un plan
  4. HITL El ingeniero aprueba el plan
  5. Harness Implementa; hooks corren lint y tests
  6. Tokens Compacta el contexto y sigue con la siguiente tarea
  7. HITL PR → code review humano → merge

Parte 3

Flujos para trabajar con IA

La ingeniería asistida, empaquetada. Misma idea: intención antes que código.

SDDODDOpenSpecBMADGSDKiroTask Master
Estos nombres circulan porque el proceso ya no cabe en un prompt. SDD es el de referencia. ODD es el de Gentleman, y en gentle-ai reemplazó a su SDD. El resto cambia cuánta ceremonia hay y quién la decide.

Las que más se repiten

FlujoQué haceHerramienta
SDD Specify, plan, tasks, implement y converge. La spec manda: cada artefacto se aprueba antes de seguir. Spec Kit
ODD Explorar, clasificar y codear con tests. Si el cambio se retoma con el diff, no hay documento. Si no, uno solo. gentle-ai
OpenSpec Proponer el cambio, aplicarlo y archivarlo en las specs vivas del repo. Más liviano, pensado para código que ya existe. OpenSpec
BMAD Aclarar, planear, construir y verificar con roles: analista, PM, arquitecto, dev y QA. El proceso crece con el cambio. BMAD-METHOD
GSD Preguntar hasta cerrar la idea, planear por fases y ejecutar cada fase en una ventana de contexto nueva. get-shit-done
Kiro Requirements, design y tasks como archivos del proyecto. No se codea hasta aprobar la fase. kiro.dev
Task Master Parte un PRD en tareas con dependencias. El agente las cierra en orden. Task Master
SDD: GitHub Spec Kit. Una constitución de principios por repo, y por feature specify, plan, tasks, implement, converge. Hay pasos opcionales de clarify, checklist y analyze. ODD: Organic Driven Development, de Gentleman Programming. Desde gentle-ai 4 el SDD salió del producto y ODD es el único flujo. Autoriza, explora, clasifica por riesgo y por si se puede retomar mañana solo con el diff. Tarea grande: un markdown en odd/tasks, copiado a Engram. Tests primero cuando hay un test que correr. OpenSpec: Fission-AI. Cada cambio vive en su carpeta (propuesta, specs, diseño, tareas) y al cerrar se archiva. Gentleman se inspiró en esto para su SDD anterior. BMAD: varios agentes con rol, para que planear y revisar no compartan el contexto de quien escribe. GSD: el problema que ataca es el context rot. Si el repo ya existe, primero mapea el código. Kiro: el IDE de AWS. Los tres archivos son requirements.md, design.md y tasks.md. Quick Spec salta las compuertas de aprobación. Task Master no es un ciclo de vida completo: es la capa que convierte un PRD en tareas ordenadas. Encaja dentro de SDD, no lo reemplaza.

Cómo elegir

Siempre la misma ceremonia

SDD, OpenSpec, Kiro. Cuando el cambio lo va a leer otra persona, o equivocarse sale caro.

Ceremonia según el cambio

ODD y GSD. Lo chico no abre un expediente. Lo grande deja algo con lo que retomar mañana.

Varios roles

BMAD. Planear, diseñar y revisar en contextos separados, como un equipo chico.

Se instalan sobre el agente que ya usas. Kiro es la excepción: el flujo vive en su IDE.

Cerrar la parte preguntando con qué están trabajando hoy. La respuesta casi siempre es "con el chat". El punto no es adoptar todos: es tener un flujo escrito, con un punto donde el humano dice que sí.

¿Entonces vibe coding es malo?

Vibe coding sí

  • Prototipos y pruebas de concepto
  • Scripts desechables
  • Aprender y explorar

Ingeniería sí o sí

  • Código en producción
  • Trabajo en equipo
  • Seguridad, datos, dinero

No es la herramienta, es el proceso.

Ideas para llevarse

  • El contexto es el nuevo código: diséñalo
  • La memoria del proyecto se versiona
  • Los tokens son un recurso, no infinitos
  • El harness y los agentes son tu infraestructura
  • El flujo se elige según el tamaño y el riesgo
  • El humano sigue siendo responsable
